一, 同根: 八成已经重叠

先卸下最大的心理负担: 这次选择没有你想象的那么重. 无论走哪条路, 下面这些都一模一样 — 它们是这个工具的躯干, 而 A/B 之争只涉及脸面.

  • Python 服务端代理执行请求. 浏览器受同源策略 (CORS) 限制, 不能随意向任意服务器发请求, 所以两条路都由你的 Python 后端代发. 选型已定为 httpx, 无争议.
  • 测试引擎. 断言用 jmespath 取值 + 比较符 + jsonschema 整体验证; 集合批量运行是自研薄层; 进 CI 时用 subprocess 跑 pytest 出 JUnit 报告.
  • 数据. 集合与环境变量存在本地, 单用户, 无账号, 无云端.
  • 运行时形态. 任何装了 uv 的机器 uv run 即起. 两条路在运行时都不需要 node.
一句顶一万句 分歧只在最后一层: 网页上那些不刷新就发生的变化, 由谁驱动. 其他所有差异 — 成本, 风险, 维护 — 都是这一个选择的推论.

二, 心智模型: 页面是怎么活起来的

一个网页最初只是服务端送来的一份 HTML 文档, 像一张打印好的纸. 让它 "活" 起来 — 点按钮出结果, 加一行请求头不刷新页面 — 有两派做法.

派别 A: 浏览器里住着一个应用. 服务端第一次送来的不是纸, 而是一整个 JavaScript 程序 (这就是 SPA, 单页应用). 此后页面上的每个字, 每行请求头, 每个标签页都活在这个程序的内存里; 服务端退化为仓库和信使 — 只管存取数据和代发请求, 对界面长什么样一无所知. Vue 就是写这种程序的主流框架.

派别 B: 服务端是大脑, 浏览器是脸面. 服务端送来的始终是 HTML, 每次有变化, 就把变化那一小块的新 HTML 再送过来 (htmx 干这个). 只有一类状态例外: 还没发送的请求草稿 — 你正在敲的字 — 交给页面上几小块独立的 JavaScript "岛" 临时记住 (Alpine 干这个), 提交时一次性交还给服务端.

图例: 方框 = 进程, 箭头 = 数据流, ● = 界面状态的住所. 两图共用同一图例.

三, 名词表

后文只用这些词, 每个一行.

  • SPA (单页应用): 整个界面是一个 JavaScript 程序, 页面不整刷, 全由程序局部更新.
  • Vue: 写 SPA 的主流框架之一, 资料最多, 同类工具 Hoppscotch 即用它.
  • node 构建链: 开发期工具 — 把 Vue 源码打包成浏览器能吃的静态文件. 只在开发时存在, 部署产物是纯静态文件, 运行时无需 node.
  • htmx: 一个小库, 让 "点按钮 → 服务端返回一段 HTML → 局部替换" 不用自己写 JS.
  • Alpine: 一个小库, 在 HTML 里直接写少量 JS 状态 (做 "岛").
  • Jinja: Python 的 HTML 模板引擎, 服务端把数据填进模板生成 HTML.
  • vendored: 把 JS 库文件直接下载放进自己项目, 不依赖 CDN, 不依赖构建.
  • 先例: 已经有人用同样技术做过同类产品 — 遇到坑可以抄答案.

四, 同一个故事讲两遍

场景: 你加一行请求头 Accept: application/json, 点发送, 看返回的 JSON.

A · SPA 版本

  1. 打开页面时, 浏览器已加载整个 JS 应用.
  2. 你敲的每个键只改浏览器内存里的草稿对象, 服务端毫不知情.
  3. 点发送 → JS 把草稿打包成 JSON, POST 给本地 Python.
  4. Python 用 httpx 发给目标服务器, 拿到响应, 原样还给浏览器.
  5. JS 把响应渲染成可折叠的树. 全程页面未刷新, 服务端不知道界面长什么样.
代码骨架 (以后回看, 现在可不读) 
<script setup>
const draft = ref({ headers: [{ key: 'Accept', value: 'application/json' }] })
const response = ref(null)
async function send() {
  response.value = await fetch('/api/execute', {
    method: 'POST', body: JSON.stringify(draft.value)
  }).then(r => r.json())
}
</script>

B · SSR 版本

  1. 打开页面时, 服务端送来一张渲染好的表单 + 几小块 JS 岛.
  2. 你敲键时, 一座岛 (Alpine) 在浏览器里记住草稿 — 因为逐键问服务端会卡.
  3. 点发送 → 岛把草稿序列化进表单, 整个表单提交给 Python.
  4. Python 执行请求, 然后自己把响应渲染成一段 HTML.
  5. htmx 把这段 HTML 塞回页面指定位置. 页面也未整刷, 但响应的 "长相" 由服务端决定.
代码骨架 (以后回看, 现在可不读) 
<form hx-post="/requests/send" hx-target="#response">
  <div x-data="{ rows: [{key:'Accept', value:'application/json'}] }">
    <template x-for="row in rows">…</template>
    <input type="hidden" name="headers" :value="JSON.stringify(rows)">
  </div>
  <button>发送</button>
</form>
<div id="response"><!-- 服务端渲染的响应片段 --></div>
手感差异 > 代码量差异 同一件事, A 的心智是 "我在写一个应用", B 的心智是 "我在写一张表单和几座岛". B 每加一个交互都要回答一次 "这事服务端做还是岛做" — 这个问题没有护栏, 答错了复杂度就开始复利.

五, 一把尺子: 逐维对比

(相同项已标出, 可隐藏)
维度A · 全自研 SPA (Vue)B · 轻量 SSR (htmx + Alpine)
后端策略 相同: httpx 执行 + 结构化断言 + 自研 runner, 数据本地, uv run 即起, 运行时无 node
运行时形态 相同: 部署产物 = Python + 静态文件, 任何有 uv 的设备即起
体验上限 高 — 对标 Postman 的顺滑, 4 个开源先例验证可行 中高 — htmx 官方自己承认与 SPA 存在交互差距; 对自用工具够用
学习成本 (零基础) 要学 Vue + JS 工具链 — 量大, 但每一步都有教程/先例/AI 熟门熟路 不学框架, 但要学 "服务端 vs 岛" 的边界判断 — 量少, 却是最难补的判断力, 且无处抄
开发成本 MVP 约 6-10 周; 组件全有成熟库可借, 自研面 30-50% 省掉构建链, 但模板工作量 +30~50%, 且岛边界要自己建模
维护成本 node 链是例行家务: 锁版本 + 季度升级约 0.5-1 天, 跟进 CVE 极低: 依赖是几个 vendored 文件, 替换即升级
同场景先例 4 个 (Hoppscotch, Bruno, Insomnia, Yaak), 组件清单可照抄 0 个 — 没有任何用 htmx 做 API 客户端的已知案例
头号风险 事务性风险: 停更库, 本地 dev server CVE — 都有例行解法 架构性风险: 岛边界失控, 复杂度反超 SPA — 无护栏, 只能重写

六, 风险肖像: 何时咬人

A 的风险 — 事务性, 有例行解法

  • 抄到过时的零件. 有些著名库已停更 (react-json-view) 或停售 (Shoelace). 解法: 照抄 Hoppscotch 的现役依赖清单, 不抄老教程.
  • 本地开发服务的攻击面. Vite/esbuild 累计 20+ 个 CVE, 恶意网页可攻击你挂着的 127.0.0.1 dev server. 解法: 定期升级, 属例行家务.
  • 流式 API (SSE/WebSocket) 难. 经 Python 代理的流式转发要自己造. 解法: v1 先砍, REST 先行.

B 的风险 — 架构性, 无护栏

  • 岛边界失控. 每个交互都要判断 "服务端做还是岛做". 判断错得多了, 状态在两边重复建模, 复杂度反超 SPA — Gumroad 的工具型产品正是因此弃坑 htmx. 这是 B 的头号风险, 且对零基础者最致命: 这种判断力恰是新手期最短缺的东西.
  • 编辑器零件的版本坑. 代码编辑器 (CodeMirror 6) 无构建链集成时, 版本错位会直接崩溃. 解法存在 (单源 vendored), 但属于 "踩过才知道".
  • 无人区. 零先例意味着搜索引擎和 AI 都给不出同场景答案, 每个坑都是首踩. 缓解: 先做三个小实验 (spike) 再正式开工.

七, 收敛成三个问题

  1. 你更怕哪种麻烦? 例行家务 (A: 定期升级依赖, 有清单可循) — 还是无人区探路 (B: 遇到坑没有答案可搜, 全靠自己)?
  2. 你要的体验是哪档? "接近 Postman 的顺滑" → A; "够用就好" → B 也够.
  3. 你对 node 构建链的厌恶有多深? 它只是开发期存在, 产物仍是纯静态文件; 若这仍不可接受 → B, 但请先 spike.
我的判断 (决定权在你) 对零基础者, 我倾向 A (Vue 3). 理由: B 省下的维护成本要靠 "岛边界" 的架构判断力才能兑现, 而那恰是新手期最短缺的; A 的风险全是事务性的, 且四个先例 + 最大生态意味着你遇到的每个坑都有人踩过, 有答案可抄. 零基础时, "每一步都有参照物" 比 "少装一条工具链" 值钱得多. 若选 A: 照抄 Hoppscotch 依赖清单, v1 砍掉 SSE/WebSocket.
