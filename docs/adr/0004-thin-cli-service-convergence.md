# CLI 瘦客户端与服务收敛执行

架构形态决策: CLI 是纯 API client (瘦客户端), 不 import 核心库 (唯一例外: launch 拉起/发现模块), 必须连本地 FastAPI 服务; 服务进程是唯一执行与安全边界, 请求执行引擎内嵌其中, 不做独立代理进程. CLI 内嵌幂等拉起: 服务在则不动作, 不在则拉起, 拉起后常驻. 进程模型一旦铺开到 CLI/服务/核心库三方, 逆转成本随调用面增长.

## 备选方案

- CLI 内嵌核心库独立运行 — 拒绝: 用户明确偏好瘦客户端, 客户端只是交互界面; 内嵌引入双执行路径 (服务/CLI 各自执行), 变量解析与历史落盘行为一致性需双份测试.
- CLI 双模 (默认 client, 连不上降级内嵌) — 拒绝: 降级路径与服务拉起失败共享同一环境病灶 (数据目录损坏/依赖缺失时内嵌同样失败), 几乎不触发却要双份测试.
- 独立请求代理进程 (Hoppscotch proxyscotch 模式) — 拒绝: 该模式为浏览器扩展/多端设计; CLI 纯 client 后执行已 100% 收敛在服务, 独立代理只剩隔离性理由, 不值一个进程加一套 relay 协议; 第二套进程管理会使拉起竞态问题翻倍.

## 后果

- 拉起可靠性成为地基: flock + 锁内二次检查 + bind(0) + service.json 原子写 + pid 存活校验 + 有限重试, 并有专项测试矩阵 (AI 代理并发调 CLI 是常态, 竞态是必然而非可能).
- 核心库唯一消费者 = FastAPI 服务, 模块间全是进程内调用, seam 少一层.
- launch 模块被 CLI 与服务共同 import, 是瘦客户端纯度的唯一例外.
- 服务常驻, 生命周期手动 (stop 子命令), v1 仅 POSIX.
